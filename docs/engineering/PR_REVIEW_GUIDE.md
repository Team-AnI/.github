# PR & Code Review Guide (A&I)

A&I의 리뷰는 사람에 대한 평가가 아니라 **코드와 시스템을 더 안전하고 읽기 좋게 만드는 대화**입니다. MOAMOA Server·Flutter의 리뷰 기준을 공통 기본값으로 사용합니다.

## 1. 운영 원칙

- **한 PR = 한 목적**: 무관한 변경은 별도 PR로 분리합니다.
- **빠르고 존중하는 리뷰**: MOAMOA 팀은 가능한 24시간 이내 응답을 권장합니다. 다른 팀은 합의한 기준을 따릅니다.
- **근거 있는 피드백**: 문제 상황, 영향, 수정 방향을 함께 설명합니다.
- **검증 가능한 승인**: Issue 완료 기준, 테스트 결과, CI, 보안·권한 및 주요 예외를 확인합니다.

## 2. 리뷰 코멘트 구분

| 표기 | 의미 | 예시 |
| --- | --- | --- |
| `[필수]` | Merge 전에 해결해야 할 문제 | 권한 검증이 누락돼 인가 테스트가 필요합니다. |
| `[제안]` | 유지보수·가독성 개선 제안 | 상태 이름을 조금 더 구체적으로 하면 좋겠습니다. |
| `[질문]` | 코드 의도·설계 확인 | 오류 응답을 나눠 처리한 이유가 있을까요? |

사소한 의견과 보안·기능 결함을 같은 중요도로 취급하지 않습니다. 확신이 없으면 먼저 질문하고, 이번 PR 밖의 대규모 변경은 별도 Issue로 나누는 것을 고려합니다.

## 3. 리뷰 흐름

1. **Conversation**에서 Issue, 작업 목적, 검증 결과, 기존 대화를 확인합니다.
2. **Files changed**에서 변경된 코드와 주변 맥락을 검토합니다.
3. UI는 접근성·화면 상태, API는 권한·계약·예외, AI는 재현성·데이터 누수 등 해당 트랙의 핵심 기준을 적용합니다.
4. 댓글을 남긴 뒤 **Comment / Approve / Request changes**를 선택해 리뷰를 제출합니다.
5. 피드백 반영 후 재검증합니다. 논의가 완료되었을 때만 **Resolve conversation**을 사용합니다.

## 4. Merge 전 체크리스트

- [ ] PR 목적과 Issue 완료 기준을 충족합니다.
- [ ] 필수 수정 및 논의가 해결됐습니다.
- [ ] 테스트·빌드·CI를 확인했습니다.
- [ ] 최소 1명의 Approve 등 프로젝트별 승인 조건을 확인했습니다.
- [ ] Merge 대상 브랜치와 민감 정보 포함 여부를 확인했습니다.

> `Merge pull request` 버튼이 활성화되어 있어도 팀의 필수 조건이 완료되었다는 뜻은 아닙니다. 브랜치 보호 규칙·필수 CI의 실제 강제 여부는 저장소별로 확인하세요.
